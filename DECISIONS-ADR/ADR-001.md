# ADR-001 — `gmail.readonly` is deferred from the phase-1 DWD allowlist

**Status:** Accepted 2026-09-01

## Context

The domain-wide-delegation scope allowlist is the only read-only control that survives someone
editing this client, so what goes on it is the security decision of the project.

The stated mail requirement is envelope metadata — who sent what to whom, when; the equivalent of
console Email Log Search. That is `reports.activities.list(applicationName="gmail")`, whose only
scope is `admin.reports.audit.readonly`. It needs no Gmail scope and no impersonation.

Separately, the mailbox-persistence audit — filters, forwarding addresses, delegates, send-as —
is high security value. Its methods accept exactly four scopes: `mail.google.com`,
`gmail.modify`, `gmail.readonly`, `gmail.settings.basic`. There is no settings-only read scope
(`analysis/API-SURFACE.md` §10). So the two read-only-ish options are:

- `gmail.readonly` — cannot write, **and reads every message body in every mailbox**
- `gmail.settings.basic` — settings only, **and can create filters and forwarding rules**

The service-account key is a bearer credential: possession alone mints tokens up to the
allowlist, with no consent step and no second factor.

## Decision

`gmail.readonly` does not go on the phase-1 allowlist. Phase 1 covers the mail-flow log, identity
and directory, Drive sharing, Calendar ACLs, Chrome, Meet and Vault.

## Consequences

- The phase-1 allowlist is **34 scopes**, all `.readonly`. A leaked key cannot read a single
  email body.
- **30 Gmail read methods are forgone**, and with them the filter/forwarding/delegate persistence
  audit — the tool's highest-value single check. This is the real cost and it is accepted, not
  overlooked.
- Mail flow is unaffected: it never needed a Gmail scope.

## Rejected alternatives

- **Keep `gmail.readonly`, gate it in the client.** The client fence is code; an AI asked to add
  a message-read tool can add one, and the allowlist would permit it. Gating in the layer that
  can be edited is not a control against the threat this project is built around.
- **Use `gmail.settings.basic` instead.** Narrower in data but write-capable — it can create the
  exact forwarding rule the audit exists to detect. Strictly worse.
- **Keep it and accept the breadth.** Defensible, and the option to revisit. Deferred rather than
  refused: re-adding is one allowlist line plus a superseding ADR.

## Revisiting

Re-add if the filter/forwarding audit becomes the priority. It is a visible Admin console change
and a superseding ADR — not a code change, which is the property worth preserving.
